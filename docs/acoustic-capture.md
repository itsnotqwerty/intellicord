# Opt-In PipeWire Output Capture Prototype

[intellicord-acoustic](../src/acoustic_cli.rs) is a separate foreground command using the shared [capture owner](../src/acoustic_capture.rs) for explicitly selected mixed-output analysis on little-endian Linux hosts. It uses the installed `pw-dump` and `pw-record` tools. Ordinary launch/injection never starts capture; the independent opt-in injected path below now connects features to the session UI. Neither path changes volume or performs moderation. Actual PipeWire capture compatibility has **not been live-validated**. Tests use generated bytes and ordinary child processes, never audio devices.

## Explicit Use

Build with the usual frontend/backend build order. The additional binary is built by `cargo build`; `cargo run` without a binary name still selects the existing Intellicord injector. PipeWire must be running and its CLI tools available on `PATH`. No privileged service or additional Rust PipeWire library is installed.

First list output sinks, without creating a recording stream:

```sh
cargo run --bin intellicord-acoustic -- sources
```

The JSON list includes only `Audio/Sink` node serials and node names, not microphone sources or application streams. Names are serialized as JSON, not written unescaped to the terminal. Node names may reveal device information; listing is an explicit action. Metadata discovery is limited to 4 MiB/three seconds and 256 output sinks. Serial values must be positive and unambiguous. Invalid or oversized metadata fails rather than falling back to default capture.

After choosing a sink, explicitly acknowledge that its entire output may be analyzed. Replace `SERIAL` with the current numeric serial from the list:

```sh
cargo run --bin intellicord-acoustic -- capture \
  --sink-serial SERIAL --acknowledge-output-capture --seconds 30
```

**This command starts real audio capture.** Selection, acknowledgement and a duration of 1..60 seconds are mandatory on every invocation. There is no remembered opt-in, default source or automatic restart. The sink is rechecked against a fresh metadata snapshot before starting. The tool requests that exact target with sink-monitor capture, no default fallback and no reconnection. These are PipeWire/tool requests, not independent proof of the connected graph. Metadata is not trustworthy speaker or application identity; concurrent changes, server restarts and session-manager behavior remain unverified. Missing sources fail or time out, not silently choose another source by application logic.

## Scope And Privacy

A sink can contain **all applications routed to that output**, including conversations, music and notifications. It is not Discord-only capture and provides no per-speaker attribution. A user-managed dedicated output sink can narrow scope, but this tool does not create or verify that routing. Microphone/`Audio/Source` and application-stream targets are not accepted through this command. A sink may nevertheless contain microphone loopback or other sensitive routed audio. The CLI cannot enforce privacy against other code or a malicious PipeWire server.

`pw-record` emits raw 48 kHz stereo native float32 to an anonymous stdout pipe, not an audio file. The parent requires a little-endian host and assembles exactly one 20 ms frame (7,680 bytes), tolerating arbitrarily split pipe reads. Each complete frame goes through the existing encoded `BufferedAcousticSession`, is consumed immediately, and its feature batch is dropped. No feature traces, PCM, participant IDs, sample timestamps or target names are written to the final report. The processor retains its usual bounded partial/history/spectral state; ordinary overwriting and dropping are not secure zeroization. Child/PipeWire/OS buffering, swap and crash dumps are outside these logical bounds. No whole-system memory or real-time guarantee is established.

The processor uses nominal sample time from zero. It does **not** create a calibrated `SampleClockMapping`, observe PipeWire hardware timestamps or detect missing source samples. Standalone capture drops features after processing; the injected path sends a bounded latest-frame summary to the shared session. The injected owner brackets nominal stream frame zero from immediately before successful `pw-record` process creation through receipt of the first complete feature frame on the backend session clock. It translates each later nominal frame position through both bracket endpoints, yielding a bounded session-time interval rather than a fabricated exact timestamp. That interval includes recorder startup, buffering and first-frame delivery uncertainty; it does not measure PipeWire or hardware time. The tool may resample/remix to the requested format; the parent trusts the external tool's raw format contract, not independently negotiated metadata. Invalid selected floats fail processing. Pipe data can be acoustically silent while still counting as valid frames.

## Injected Session Integration

The following is an operator invocation, **not a validation command**. It starts
real mixed-output capture after successful client injection. Choose a current
sink serial with the separate `sources` command first, and review the privacy
scope above before using it:

```sh
npm run build
cargo build --locked
./target/debug/intellicord inject --port 9222 \
  --acoustic-sink-serial SERIAL --acoustic-seconds 30 \
  --acknowledge-injected-output-capture
```

The same complete policy can be passed to `intellicord launch` instead of
`inject`; launch uses fixed loopback port 9222 and automatic target selection.
This is explicit per-invocation activation only. The installed desktop entry
passes no acoustic flags and remains sensor-free. A configured launch refuses to
silently merge into an Intellicord launcher that already owns the Discord
session; stop that session before retrying.

All three acoustic options are mandatory and validated before DevTools access.
Consent is not persisted and is not implied by process-observation consent.
Explicit process observation and acoustic capture can run together; each retains
its own lifecycle and failure status. By default, capture starts after successful
injection. Add `--defer-acoustic-start` to prepare a one-shot client confirmation
instead. The renderer can then start only that already selected sink and duration;
it cannot select, reconfigure, restart or retry capture. The desktop launcher
cannot enable capture. The trusted backend resolves PipeWire tools through its
inherited `PATH`, as does the standalone CLI.

In deferred mode, Safety & Intelligence shows Play only while the current
session has both the prepared capability and a validated active voice call.
Confirmation repeats that all applications on the selected output may be
analyzed. The strict command contains only
`acoustic_start` and the current `session_id`; malformed, stale, duplicate and
unconfigured requests, including requests without an active call, are no-ops.
Acceptance consumes the start capability, binds the owner to the active call and
exposes stop capability, but the review waits for an acoustic summary before
reporting capture. Ending or switching that call requests the same supervised
capture stop; it does not retry on a later call. Pending state survives closing
the review; send failure or a five-second timeout does not imply capture and
never retries. Detaching before confirmation cancels the owner without starting
`pw-dump` or `pw-record` and without manufacturing a terminal acoustic summary.

The session view carries a separate bounded acoustic-owner lifecycle:
`not_configured`, `prepared`, `running` or `finished`, plus whether the request is
call-bound. It does not export the bound call or channel ID. A finished owner
reports `completed` or `faulted`, whether cleanup was confirmed, and in owner
schema 2 a bounded fault category from the machine-readable lifecycle vocabulary.
Completed runs use a null reason because the reusable capture API intentionally
does not distinguish duration expiry from owner-requested stop. This contains no
sink identity, diagnostic text, audio-derived data or liveness claim. Processing,
source and startup failures can therefore remain classified faults while still
confirming that owned tools were absent or reaped; a cleanup failure is shown
separately as unconfirmed. Older schema-1 clients can continue using the outcome
and cleanup fields alone.

Automatic reconnect remains disabled. Rediscovering the same numeric serial does
not prove that it still identifies the consented physical sink, and deferred
capture is a one-shot request bound to one accepted call. Source loss therefore
ends the owner with a bounded fault category and requires a new explicit request.

Recorder startup now performs a second bounded metadata snapshot before creating
the acoustic processor or accepting PCM. The selected serial must still identify
an `Audio/Sink` with the same bounded node name as the first snapshot. A missing,
reclassified or renamed node stops and reaps the already-started recorder, emits
`source_rejected`, and retains no frame. Cancellation during this check also
reaps the recorder and completes with zero frames. This narrows the discovery-to-
startup replacement window; serial plus node name is not a hardware identity,
and the check does not establish later source continuity or liveness.

The backend also reduces this owner and the optional process owner into a strict
`session_sensors` lifecycle aggregate. It contains only configured, pending and
finished owner counts plus `sensor_free`, `pending`, `settled` or `attention`
status and combined cleanup state. Safety & Intelligence and Session Health show
that verdict before the two detailed owner sections. An acoustic fault, process
fault, unavailable owner or unconfirmed cleanup requires attention. This does not
merge feature samples, align clocks, establish liveness, attribute mixed output
or contribute evidence to participant findings.

The reusable capture owner publishes reduced feature frames through the existing
64-message sensor bus. Messages contain source provenance, sample-relative frame
start, RMS, peak, near-full-scale ratio and discontinuity. Version-2 frames may
also contain six latest-only scalars reduced from the already-computed spectral
and repetition result: centroid, high-band power ratio, positive power flux,
compared-lag count, best coarse lag and its similarity. They never contain PCM,
spectral bins, normalized power, descriptor vectors, device names/serials or
participant IDs. Backend receipt timestamps use the session's `Instant` origin.
Injected mixed-output frames promote the summary to version 3 and add the
earliest/latest backend-session time derived from the recorder-start bracket.
The original sample-relative position remains explicit. This permits bounded
ordering against backend receipt time, but is not calibrated synchronization to
voice events; process health counters expose freshness only and have no event
clock to correlate.
One summary retains accepted frame/discontinuity/message-gap counts and the last
frame. The strict client still accepts the prior level-only version-1 summary;
version 2 requires an `analysis` key, which may be null for a level-only producer,
and version 3 additionally requires the exact bounded session interval.
Runtime version 4 additionally requires the latest bounded `OutputHealth`
snapshot already produced by the owning processor. The bus validates fixed queue
capacity, pending/high-water bounds and exact processed = delivered + discarded
+ pending conservation for both batches and frames. Fusion also requires source
and active/stopped/faulted state agreement. Safety & Intelligence displays these
as in-process queue accounting; Session Health surfaces discarded frames or
overflow as attention. The snapshot does not establish source, recorder,
PipeWire, device or downstream renderer liveness.
There is no acoustic history, content fingerprint export, calibrated scoring,
participant attribution or automatic action. Similarity is a coarse latest
comparison, not a classifier, abuse probability or robust fingerprint.

While configured, the session drains the bus every 200 ms and sends the summary
in the existing view. Safety & Intelligence and Session Health distinguish
starting, frames received, stopped and faulted. These are last-received states,
not heartbeat-based liveness. Source labels warn about all applications on the
selected output. Missing or invalid summary data clears the detailed view; review
reset preserves current acoustic status and ingestion counters. Acoustic data is
not included in participant evidence exports.

Safety & Intelligence includes a stop icon only for an acknowledged, current
mixed-output capture with a supported summary and explicit backend stop
capability. It sends only `acoustic_stop` and the current `session_id`. The backend
requires exactly those fields, a matching session and an outstanding capture;
stale, malformed, duplicate and unconfigured requests are no-ops. It revokes the
capability immediately, but that acknowledgement does not mean cleanup finished.
The review waits for a terminal summary before reporting a stop. Pending state
survives closing and reopening the review; a five-second timeout reports an
unconfirmed result and never retries automatically. A fault does not confirm
cleanup. Session replacement or missing/invalid data clears the request state.

Stopping does not detach the menu, interrupt voice tracking, stop process
observation or reset retained evidence. It does not grant renderer authority to
restart or reconfigure capture. Cancellation during discovery prevents
recorder startup; the injected owner reports a normal stop only after discovery
cleanup succeeds. This differs from the standalone CLI's nonzero startup-signal
contract below, which remains unchanged. Discovery cleanup failures propagate
instead of claiming a clean stop. All shutdown bounds remain cooperative.

Publishers do not block on full queues. Drops are counted in shared ingestion
metrics, and a later acoustic sequence gap records missing messages, not missing
source samples. Intermediate states may coalesce or be lost. Owner completion
also uses a separate one-shot notification, drained after queued features, so a
full bus cannot hide the final stopped/faulted result. This notification carries
no extra audio data. It does not add crash or hard real-time guarantees.

Capture failure leaves voice tracking running and does not retry. Duration expiry
ends capture without detaching the menu. Tracking return, including reload or
handled SIGINT/SIGTERM, cancels capture and awaits its existing discovery/recorder
teardown before client disposal and binding removal. On normal detach, capture
failure produces a nonzero exit; a tracking error keeps its own cause unless the
separate process-owner policy reports its own failure. Forced abort/SIGKILL and
uninterruptible OS work remain outside awaited-cleanup guarantees.

## Status And Shutdown

Before spawn, stderr identifies the requested serial, duration and mixed-output scope. While running, a once-per-second `CAPTURE REQUEST ACTIVE` message reports analyzed frame count and the stop action. This describes the outstanding capture request, not verified signal flow or source identity. Zero frames can mean connection startup; complete frames, including silence, establish byte delivery only. The command should remain visible in the foreground.

Ctrl+C, SIGTERM or the duration deadline stops processing, terminates and reaps the recorder child, then prints `CAPTURE STOPPED`. A normal stop emits one JSON report with schema version, stop reason and stopped output-health counts. Complete frames are counted as delivered by the local processor, not receipt by another consumer. Final incomplete raw bytes are discarded, not padded or counted as a complete frame. There is no downstream consumer in this command.

The duration begins before metadata discovery, not after recorder startup. During capture startup, the same signal/deadline future also cancels discovery and tears down its child. A pending stop is checked again immediately before recorder spawn. Cancellation before startup exits nonzero with a bounded reason on stderr, no success JSON and no recorder launch. It does not print `CAPTURE STOPPED` because recording never began. This prevents a signal received during slow discovery from being followed by capture starting. The separate read-only `sources` subcommand retains its three-second discovery timeout; this capture-specific cancellation contract does not add signal-driven reporting to that subcommand.

Unexpected child exit, EOF, invalid PCM, read errors or three seconds without a complete frame fail closed, tear down the processor and recorder, and exit nonzero without a success JSON report. Diagnostic errors go to stderr; external tool stderr is suppressed. No reconnect is attempted. Stop waits for synchronous frame analysis to return, so this is not a hard real-time deadline. Graceful paths kill and reap; Rust child `kill_on_drop` is a fallback, not a guarantee under SIGKILL, process/runtime abort, power loss or a hung kernel. There is no service-manager or crash-recovery supervision yet.

## Machine-Readable Lifecycle

Add `--status-json` to an explicitly acknowledged `capture` request for versioned newline-delimited JSON on **stderr** instead of human status. The option does not imply consent, change the selected sink or enable capture from the injector. Stdout remains one final success report on a normal stop and empty on failure. Default invocations keep their existing human stderr and final stdout format.

Each status record contains exactly `schema_version` (currently `2`), `record_type` (`capture_status`), contiguous `sequence` starting at `1`, `phase`, `reason`, `recorder_reaped` and `health`. `reason` is null for nonterminal phases and a bounded enum string for terminal phases. `health` is either null before processing or the existing bounded `OutputHealth` schema. No audio features, PCM, target serial/name, participant identifiers, timestamps or arbitrary error text are included. A consumer must recognize the schema version and process exit status, not treat any single progress event as proof of successful capture. Version 2 supersedes the earlier version 1 status protocol; consumers pinned to version 1 must explicitly update, not assume the field set is unchanged. The final stdout report and nested output-health schemas remain version 1.

The normal phase sequence is `discovering`, `recorder_requested`, `awaiting_frames`, `receiving_frames`, `stopping`, `stopped`. `recorder_requested` precedes spawn and does not prove a running recorder. `awaiting_frames` means the processor is ready but has delivered no frames. The first complete, validated, locally consumed frame produces `receiving_frames`; health updates in that phase follow approximately once per second. Silent frames qualify. This establishes byte delivery under the requested format contract, not acoustic activity, correct routing or source identity.

An accepted request that fails instead ends in `faulted` when status delivery remains available. Startup cancellation uses that phase too, with `interrupt`, `terminate` or `duration_limit` identifying cancellation rather than an unexplained sensor fault; it is not a successful capture stop. Startup faults have null health and `recorder_reaped: false`, which means no recorder-cleanup confirmation, not evidence that a recorder remains running. Active processing faults preserve pre-stop fault health in the terminal record; the preceding `stopping` record contains the already-stopped processor health. `recorder_reaped: true` appears only after recorder termination/wait succeeds. Cleanup errors do not claim reaping. The boolean concerns the recorder, not metadata discovery. Invalid arguments can exit before any status records exist.

Terminal reasons are selected by typed control-flow context, never by parsing diagnostic strings:

| Reason | Meaning |
|---|---|
| `duration_limit`, `interrupt`, `terminate` | The requested stop condition was observed; normal active stops also repeat this reason in stdout. A stop before recorder startup instead exits nonzero. |
| `discovery_failed` | Metadata tool launch, read, exit, validation or discovery deadline failed. These subcauses are intentionally grouped. |
| `signal_setup_failed` | Unix signal handlers could not be installed. |
| `source_rejected` | The requested serial was not in the accepted fresh output-sink list. |
| `recorder_start_failed` | Launching the recorder failed. |
| `input_stalled` | No complete frame arrived within the frame timeout. |
| `stream_ended` | The parent observed EOF, including an incomplete final frame. |
| `stream_read_failed` | Reading recorder bytes failed. |
| `processing_failed` | The acoustic processor rejected input; fault health provides the existing bounded detail, such as `invalid_sample`. |
| `delivery_failed` | Local processor output retrieval failed or its required batch was missing. |
| `recorder_exited` | Waiting on the recorder completed unexpectedly or failed. |
| `cleanup_failed` | Recorder termination/wait did not complete successfully; no reaping confirmation is emitted. |
| `internal_failure` | An otherwise unclassified controller failure; it is not inferred from arbitrary error text. |

EOF and recorder-exit notification can race; either `stream_ended` or `recorder_exited` can describe a child exit, depending on which fact the parent observed first. These are local observations, not a diagnosis of the underlying PipeWire failure. If cleanup itself fails, `cleanup_failed` takes precedence because shutdown confirmation is unavailable. Signal-setup, read, delivery and cleanup categories are defined contracts, but not every OS failure can be induced by the executable fixture suite.

The [status writer](../src/acoustic_capture/status.rs) serializes records smaller than 2 KiB through a dedicated thread, a one-record channel and a 100 ms acknowledgement timeout. The controller waits for one write at a time; it does not accumulate a per-frame event queue. A closed, stalled or failed output stream aborts processing and invokes recorder cleanup without waiting for that writer thread. The timeout bounds the acknowledgement wait, not OS scheduling or the complete shutdown path. A terminal record is not guaranteed when output fails, and a write acknowledgement is not proof that the consumer read it. In this mode errors are represented by status plus nonzero exit, without a fallback human stderr write that could block shutdown. Default human terminal output retains its synchronous behavior. A future UI must continuously drain both pipes and treat EOF/nonzero exit or missing terminal status as incomplete lifecycle information. This is a CLI protocol foundation, not an integrated capture UI or crash supervisor.

## Validation And Remaining Work

```sh
cargo test --lib acoustic_capture::
cargo test --test acoustic-capture-cli
cargo test --test acoustic-ingestion --test acoustic-injection
```

Eight tests cover explicit consent/target/duration/status-option parsing, output-only metadata filtering and limits, exact no-fallback raw recorder arguments, generated PCM fragmentation/partial tails, invalid PCM/EOF/stall rejection, child termination/reaping on stop and timeout, typed-context classification independent of misleading text, and simulated stalled-writer timeout with no further queued output. Actual executable help and invalid requests were checked without PipeWire tools available. Installed `pw-record --help` was inspected without creating a recording stream.

On 2026-11-21, an explicitly approved release run attached to Discord desktop
1.0.170 and selected the current default PipeWire output by its enumerated serial.
The real recorder delivered 250 complete 20 ms frames over five seconds through
the injected processor, then the duration limit stopped and reaped it. The
combined injector later removed its renderer lifecycle and left Discord running;
no Intellicord or `pw-record` process remained. No audio file was written. This
single run does not prove signal content, physical source identity, compatibility
with other sinks or PipeWire versions, ongoing source continuity, crash cleanup
or resource bounds.

Fifteen additional Linux executable tests substitute [fake PipeWire tools](../tests/fixtures/pipewire-tool.mjs) on each child command's isolated `PATH`. They need Node.js on the developer's `PATH`, as does the frontend toolchain. A temporary Unix socket provides readiness/PID notifications so tests send real SIGINT/SIGTERM only after startup, not after a guessed delay. The [tests](../tests/acoustic-capture-cli.rs) cover signals during discovery and active generated-byte processing, deadline expiry in both stages, invalid PCM, recorder exit, stalled output, microphone-class target rejection and missing consent. They check exit/report shape, stopped health, no success JSON on failures and absence of known fixture child PIDs after exit. JSON-mode tests pin record fields, sequence/order, zero-frame versus delivered-frame status, startup cancellation, preserved processing fault health and recorder reaping. The reason matrix covers active signals, discovery deadline/invalid metadata/missing tools, target rejection, EOF while the child remains alive, recorder exit and stalled input. Missing-tool tests restrict `PATH` to the fixture directory so they cannot fall through to real PipeWire tools. Closed consumers are tested before discovery and during active generated-byte processing; those failures emit no success report and active recorder children are reaped. Temporary files contain fixture code/socket metadata, not audio recordings. Fixtures have a bounded watchdog for failed-test cleanup and never connect to PipeWire. These checks verify executable orchestration, not real graph selection, real-time guarantees or device shutdown under actual PipeWire.

The injected integration tests run the real backend against fake DevTools and
fake PipeWire tools, then feed actual view JSON through the production menu in a
Node/LinkeDOM renderer. They cover generated PCM and deadline completion, rejected
sources and invalid PCM, voice departures after acoustic delivery/failure, active
SIGINT/SIGTERM, slow-discovery cancellation, and concurrent invalid-object process
observation. A repeated-tone case verifies centroid and coarse repetition values
through capture, bus ingestion, versioned JSON, strict parsing and the production
review, including concurrently configured process observation; it verifies that
participant observations contain no acoustic fields. Stop-only cases use actual menu commands, reject stale/malformed
requests while frames continue, tolerate duplicate stops, and verify voice
departures after stop. Fixture PIDs must disappear before stop acknowledgement
as well as binding removal. These tests
require `npm ci`; they never attach to Discord or connect to PipeWire.

Still unfinished: verified application-only routing, native buffer/format/source
monitoring, measured clock mapping, in-client capture startup consent/selection, worker
isolation and measured resource budgets, robust crash cleanup, reconnect handling,
cross-sensor correlation, calibrated acoustic scoring, representative evaluation
and reversible attenuation. The full per-session capture milestone remains
incomplete; bounded CLI opt-in, automatic session status, and backend-derived
session evidence integrity are now connected. The aggregate can report an
acoustic frame as independently usable or processing loss as degraded, but it
does not identify a source, establish liveness, or correlate that frame with a
voice/process event.
