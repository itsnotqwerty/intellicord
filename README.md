# Intellicord

A Rust-backed, opt-in enhancement project for the Discord desktop client. Callmon is one of its first major features: a small JavaScript adapter observes the client's existing voice stores and renders a compact menu while Rust computes and retains join/leave history. No BetterDiscord or Vencord installation is required, but Discord must explicitly expose its Chromium DevTools endpoint.

**Status:** working core, injector, and interactive preview. Live attachment, active-call detection, and observed membership activity were verified on Discord stable desktop 1.0.169, web build 673869. On desktop 1.0.170, a bounded combined owner run also attached successfully, processed five seconds of live PipeWire output, and completed five seconds of capability-brokered eBPF observation. The collector loaded and attached the reviewed tracepoint object, delivered four periodic health samples, stopped at its duration limit, explicitly detached, reaped, removed its private endpoint, and left Discord running; the recorder and renderer also cleaned up. This is one-host bounded compatibility evidence, not sustained-operation, event-completeness, attribution, or cross-clock-correlation proof. Other releases, call types and sinks remain unverified. Discord has no official vanilla-client plugin API. Its private stores, module cache, and debugging flags may change or be unavailable. Client modifications are unsupported and may violate Discord's terms or create account risk; review those terms before using this with an account.

## Build

Requires a recent Rust toolchain supporting edition 2024, Node.js 20+, and npm.

```sh
npm ci
npm run build
cargo build
```

Build the JavaScript first: Rust embeds `dist/client.js` in the executable at compile time. Rebuild both after changing the adapter or menu. The compiled executable needs neither Node.js nor a separate web server at runtime.

Development and test builds use one Cargo job, one LLVM code-generation unit,
disabled incremental compilation, and a 32 MiB compiler-thread stack. These
repository-local settings mitigate intermittent compiler SIGSEGVs observed with
both Rust 1.100.0 and a freshly installed 1.99.1. Limiting Cargo jobs alone did
not prevent the fault. Clean builds with the combined settings passed, but the
underlying compiler or host-instability cause remains unconfirmed. Compilation
is slower; release profile settings and the explicit eBPF nightly are unchanged.
Explicit environment overrides can supersede these defaults.

Open [preview.html](preview.html) after building the JavaScript for an interactive preview with explicitly labeled demo data. It uses the same menu as the injected plugin. No Discord login or server is needed for the preview.

The Rust package and executable are named `intellicord`, and the private JavaScript package is `intellicord-client`. Callmon remains the voice-history feature name, including its Markdown-log filenames. The internal `__callmon_send` binding and `__callmon` lifecycle alias are retained for transport compatibility; `__intellicord` owns the combined feature lifecycle.

## Attach To Discord

On Linux, run `./scripts/install-user.sh` to install `~/.local/bin/intellicord` and a user-local Discord desktop launcher that runs `intellicord launch`. This default mode remains sensor-free. `./scripts/install-user.sh --with-live-sensors` additionally builds the pinned eBPF target, verifies its offline layout, compiles the host with `observe`, and stages compatible user-owned artifacts. It requires the dated nightly, `rust-src`, and `bpf-linker` described in the process-observation guide. It does not grant privileges. `sudo ./scripts/install-bpf-helper.sh` is a separate reviewed administrator action: it installs root-owned, non-writable copies of the object and collector, installs a dedicated fixed-command broker, and grants only that broker `CAP_BPF`, `CAP_PERFMON`, and `CAP_DAC_READ_SEARCH`. The last capability is needed to read root-only tracefs event metadata; the broker's fixed artifacts and cleared environment limit that otherwise broad filesystem-read bypass. The general observer and authenticated Discord injector receive no file capabilities. The broker accepts no object path or general observer command, requires a same-user target and its actual parent PID, then replaces itself with the fixed collector so existing peer credentials and reaping remain authoritative. `sudo ./scripts/uninstall-bpf-helper.sh` removes these protected artifacts without touching running processes. Neither installation command loads or attaches BPF, starts PipeWire capture, or modifies a running process; every live session still requires the complete command-line policies above. Subsequent desktop launches remain sensor-free and attach automatically using loopback-only DevTools. An already-running non-debuggable Discord instance must be quit and relaunched by you; the installer never changes running processes. Updating the installed binary does not restart the active backend, so backend protocol changes take effect on its next launch. `./scripts/uninstall-user.sh` removes the managed launcher and user-owned binary/artifacts and restores a backed-up custom launcher, without stopping Discord.

For manual attachment:

1. Fully quit Discord, including its tray process. Starting another instance usually forwards to the existing process and ignores debugging flags.
2. Start Discord yourself with a loopback-only debugging endpoint:

   ```sh
   discord --remote-debugging-address=127.0.0.1 --remote-debugging-port=9222
   ```

3. Log in normally and wait for the client to load. Confirm the endpoint is not listening on a public/network interface:

   ```sh
   ss -ltnp '( sport = :9222 )'
   ```

4. In a separate terminal, attach:

   ```sh
   cargo run -- inject --port 9222
   ```

Keep the Rust process running while using Intellicord. Ctrl+C removes injected features, listeners, and binding. Restart Discord without debugging flags afterward to close the endpoint. The executable is `target/debug/intellicord`; the workspace directory need not be renamed.

The endpoint grants full access to your logged-in renderer. **Never expose or forward it to another machine.** The injector connects only to a loopback websocket on the specified port and accepts only Discord app/channel pages. Those checks do not make an exposed DevTools endpoint safe. No tokens, passwords, or account credentials are required by Intellicord.

If several Discord pages are available, the injector prints their target IDs; select one with `--target ID`. If your build disables remote debugging or does not expose the required webpack cache/stores, this prototype cannot attach. It deliberately does not patch installed files, bypass those restrictions, or enable Node integration.

After a Discord page reload, run the injector again. If the backend was forcibly terminated, reload Discord first to discard its orphaned menu. A second injector refuses to replace an existing instance.

Safety & Intelligence also combines owner integrity, current process-sample usability, and acoustic frame/processor integrity into a strict session-evidence verdict: sensor-free, awaiting, partial, independent, or degraded. “Independent” means both streams are usable separately, never that their events are correlated. The timing inventory distinguishes shared backend receipt time, bounded acoustic frame intervals, capture-relative timing, and process freshness without an event clock. It always reports calibrated cross-sensor correlation as unavailable. The combined lifecycle verdict reports owner completion and cleanup only; recent counters expire locally and neither verdict establishes source liveness or participant attribution. Diagnostic copying remains privacy-limited.

## Behavior And Privacy

- Records observed joins and leaves in the user's currently connected voice channel, including users moving into or out of that channel. It does not monitor other channels.
- Existing participants establish a baseline when attaching, joining, or switching calls. They are not falsely logged as new joins. Disconnecting or switching your own call does not fabricate departures for everyone in the previous call.
- Joining a new call archives the previous call's history and starts a fresh current-call view. This includes rejoining the same channel after disconnecting. Disconnecting alone keeps the last call's history available until the next join. Baseline-only calls are archived too, without fabricating activity.
- The call-history selector appears when archives exist and lists previous calls by channel and start time, newest first. Archives are read-only; user/action/search filters and Markdown exports apply only to the selected call. Joining a new call automatically returns to the current-call view. Archive entries and user menus retain their original channel context.
- Retains at most 20 archived calls and the latest 500 events shared across the current call and archives for this injector session. Oldest archives are evicted beyond the call limit; oldest archived events are removed first beyond the event limit. History and archives are memory-only, with no disk persistence, telemetry, uploads, or historical backfill, and are lost when the backend stops.
- Displays global display names and usernames as observed at the time of an event; server nicknames are not yet supported. IDs remain strings end to end, avoiding JavaScript numeric precision loss.
- Shows observation timestamps, newest first, with All/Joined/Left filters and username/ID/channel search. Row info icons open an event explanation with exact user/channel IDs, observed timestamps, call boundaries, raw action, and retained reconnect links. Each field and the complete text/JSON can be copied, with selectable fallback on clipboard denial. Identity Lens and Voice Watch are available inside event details. Clearing current-call history requires confirmation, keeps the current membership baseline, and does not clear archives or recap counters.
- A participant leaving and returning to the same observed call within 30 seconds is labeled **Probable reconnect**. Both raw leave and join events remain intact, including their sequence link and observed gap. This is a timing heuristic, not a diagnosis of a network failure. Switching calls or disconnecting resets pending reconnects; up to 10,000 pending leaves are kept in memory.
- Opening the current-call monitor shows a **Since last checked** digest of retained arrivals, departures, and probable returns. Paired reconnects are grouped without changing raw events. Activity observed while viewing the current call is considered checked; viewing an archive does not consume current-call changes. Call switches reset the digest, and unseen events lost to Clear or retention are explicitly counted as unavailable. The digest does not produce notifications.
- Ended **private group calls only** offer a Call recap control. Eligibility requires Discord group-DM channel type `3`; direct messages, guild voice calls, and unknown types do not receive recaps. Recaps report observed duration, baseline participants, unique retained participant IDs, peak attendance, joins, leaves, and probable reconnects. Baselines are not joins, observed duration may begin after the actual call started, and counters survive event clearing/trimming. Each recap retains at most 10,000 participant IDs and warns if truncated. Recaps share the existing memory-only call archive lifetime.
- When another ended recap has the exact same group channel ID, a comparison picker shows duration/attendance/activity deltas plus shared and different retained participant IDs. Different groups, non-group calls, and ongoing calls are never comparison candidates. Copies are explicit local clipboard actions, not automatic disk storage or uploads.
- The user-filter icon opens a searchable checklist of recorded users and current callers. Selection uses exact user IDs, combines with the search and event-type filters, and does not alter history. All users restores the full selection; selecting nobody produces no matching events. Current callers appear even before any activity has been recorded, without fabricating join events.
- The download icon exports only matching events from the selected call to a UTF-8 Markdown (`.md`) log with a heading, export metadata, call channel/start/end details, and an activity table, oldest first, with UTC ISO timestamps, join/leave actions, usernames, display names, exact user IDs, and channel details. Fields are escaped to prevent names from injecting Markdown, HTML, table columns, or forged log entries. Export is disabled when nothing matches. This explicit download is the exception to memory-only storage; saving is handled by the client/browser, and downloaded files remain until you delete them.
- Right-click an activity entry or user-checklist row to open Discord's actual user context menu. Shift+F10 and the Context Menu key work on focused rows too. Discord supplies the profile, message, mute, volume, moderation, and other actions according to the user, channel, and your permissions. Historical entries retain their original channel context; unavailable users/channels and unsupported native menu APIs show a visible error while history remains usable. Callmon does not undo actions taken from this menu.
- Native user menus can be lazy-loaded by Discord. If the component is not already loaded, Intellicord parses the native call site's chunk-loading expression and requests its declared chunks through Discord's runtime. It does not evaluate extracted source. Unsupported loader shapes and chunk-download failures show a visible error; keyboard targets are retained while loading.
- While attached, native `user-context` menus with a Copy User ID item gain **Look Up Public Profile** immediately below it. Clicking opens Leakfun's Discord lookup in a new browser tab/window, with the exact user ID, `source=universal`, `autorun=1`, `mode=lookup`, and a fresh random `autorunToken`. No lookup request is made merely by opening the menu. The link omits the referrer and prevents opener access; clicking explicitly sends the ID to this third-party service, whose account requirements and data practices are outside Intellicord's control. Public-profile-only behavior is based on the user's description and has not been independently verified. Message/channel/server menus are not modified, and detach removes the shortcut. The item requires Discord's native Copy User ID item to be present (typically Developer Mode).
- User pictures use Discord's native avatar URL with a validated avatar-hash fallback. Only HTTPS Discord CDN/media profile-image paths are accepted, image requests omit the referrer, and initials remain available when an image cannot load. Displaying pictures makes normal CDN image requests; Callmon does not persist pictures or identities to disk.
- Uses Discord font/color variables where available, compact spacing, muted metadata, familiar icons, and small-radius surfaces. Callmon's launcher follows the bottom-left of the visible call view, not the application corner; its popup is clamped to the viewport. It hides when the call view is absent or user settings are open. Scroll, viewport changes, call-view replacement, and element resizing refresh its position.
- Listens to voice and selected-channel store changes, with a one-second reconciliation poll. Very short transitions that are not exposed by those stores can be missed. Missing users or unsupported snapshots pause capture instead of producing false departures. Recovery records the next observable difference, not unobserved intermediate activity.
- Ordinary launch/injection captures no audio. Explicitly acknowledged output analysis processes mixed-output PCM in memory and sends only bounded level summaries to the session UI. Neither mode captures messages, friend lists, or authentication tokens. Usernames and IDs are still personal data; use the history responsibly and avoid sharing it unnecessarily.

## Sponsored Content

Intellicord adds **Disable Quests and Sponsored Content** at the head of **Settings > Data & Privacy > Sponsored Content**. It is off by default. Enabling it hides recognized Quest and sponsored UI surfaces, including supported cards, prompts, and navigation links, and continues filtering elements added after navigation. Turning it off or detaching restores the elements. The switch remains accessible, and Discord's native privacy controls are excluded from filtering.

This is **client-side UI suppression only**, not an account-wide or network-level disable. It does not stop Discord fetching content, measuring activity, progressing accepted Quests, or sending notifications outside the injected renderer. Discord's two native personalization opt-outs explicitly say Quests may still appear; Intellicord does not change those settings or claim a complete service-level opt-out. Keep using native privacy settings for personalization choices. Other surfaces or future builds may need new adapter selectors.

Suppression preferences are persisted as independent booleans in `$XDG_STATE_HOME/intellicord/preferences.json` (default `~/.local/state/intellicord/preferences.json`) by the Rust backend; no call history or identity data is written there. Existing single-preference files migrate with the additional switches off. On Linux, the directory is owner-only and the file uses mode 0600. This works even when Discord denies renderer localStorage access. Each switch waits for backend acknowledgement before changing suppression. Storage failures display an error and leave the setting unchanged. Preferences stay saved when detaching, but suppression applies only while Intellicord is attached. They are local to this OS user, not synchronized to your Discord account.

## Utility Plugins

### Safety & Intelligence Prototype

The initial architecture milestone adds a versioned Rust observation contract and a bounded fusion log fed by existing validated voice-history differences. Snowflake IDs remain strings. Initial participants and channel switches establish baselines; duplicate transitions are ignored. Sources distinguish store notifications, initial capture, reconciliation, and legacy/unknown input. Timing uses backend `Instant` for intervals and UTC Unix milliseconds for display; renderer/transport delay is explicitly unmeasured.

The log retains 512 observations and 50 incidents, with at most 20 embedded evidence observations per incident. Retention evictions and known missing transitions have separate counters. Unchanged voice capture sends a low-rate health snapshot; recovery after capture failure, receipt gaps over five seconds, and monotonic rollback reset correlation and create explicit gap records. No missed intermediate joins/leaves are invented. Gap detection requires another sample to arrive, and it cannot count unseen transitions.

Two fixed experimental rules group five distinct arrivals or three leave/return pairs within ten seconds of receipt time, with a 30-second per-rule/call cooldown. **These thresholds are not calibrated and do not establish abuse, coordination, automation, or network cause.** Normal group arrivals, reconnects, and delayed samples can explain the same facts. The review shows exact evidence, source, timestamps, limitations, and detector version. It has no connection to Obliterate or other moderation execution.

Application frames pass through a typed **64-message in-process sensor bus**. Publishers never wait for queue space; overflow rejects the newest message. A gap in the application producer's sequence resets correlation and suppresses inference from the recovery frame, without discarding valid earlier findings or attributing diagnostic loss to participants. Fusion rejects stale sessions, replayed producer messages, backwards producer clocks, and invalid call/history progression. Voice payloads are size-limited, carry IDs rather than usernames, and cannot be submitted as diagnostic reports. Explicit output capture now has its own feature-only producer lane, sequence guards and bounded summary, without adding acoustic measurements to participant evidence or incidents. Its version-2 summary retains levels plus only the latest spectral centroid, high-band ratio, positive flux, coarse lag count and best lag/similarity; it carries no PCM, spectrum, descriptor vector or acoustic history. Injected mixed-output frames use version 3 to add an earliest/latest backend-session interval obtained by bracketing recorder startup. Runtime version 4 additionally retains the processor's bounded queue accounting: processed, delivered, pending and discarded frames, overflow count and queue high-water depth. Conservation, source and lifecycle consistency are checked before display. These counters describe in-process disposition, not PipeWire/device liveness or downstream client receipt. The timing interval is not a calibrated PipeWire or hardware timestamp, and derived values are not classifiers. While capture is configured, a 200 ms drain publishes acoustic summaries on the existing session view; owner completion is delivered independently of queue overflow. Producers share the backend receipt clock domain; process health has no event clock, and acoustic source timing remains uncalibrated against voice events.

The review's **Ingestion health** section separates accepted/rejected inputs and dropped queue messages from retained observation/incident evictions and known missing voice transitions. Diagnostic state is the last accepted report, not a liveness guarantee, and starts as **Not connected**. Tests cover concurrent publishing, boundedness, overflow recovery, producer/session isolation, replay rejection, and the real loopback transport.

The review's download icon explicitly requests an `intellicord-evidence.md` file containing all retained observations (up to 512), incidents (up to 50), and their embedded evidence (up to 20 observations each), not just the visible rows. Whitelisted fields include exact string IDs, source, times, history sequence, detector version, uncertainty, gap/retention counters, and session ingestion health. When present, strictly parsed backend session contracts add a reduced integration-boundaries section with owner/evidence verdicts, timing inventory, acoustic terminal outcome, and processor accounting. It contains no raw errors, sink or call identity, PCM, acoustic history, or process sample counters. Process freshness is valid only at backend publication time; the static export does not establish continuing liveness, attribution, source identity, or calibrated cross-sensor correlation. Untrusted fields are escaped for Markdown; malformed optional integration fields render as unavailable instead of leaking unknown content. Unsupported/incomplete retained evidence fails visibly rather than exporting a misleading partial report. Downloading is a user-initiated disk-storage exception to memory-only operation. The file contains personal IDs, is not uploaded by Intellicord, and remains until you delete it. Browser download handling is responsible for saving the file.

The trash icon offers a separate confirmation, defaulting to Cancel, to reset intelligence observations, incidents, embedded evidence, detector windows/cooldowns, and review loss counters. The backend acknowledges the reset before the UI reports success. Capture continues; Callmon history/archives, membership baselines, session IDs, replay guards, and session-lifetime ingestion health are preserved. Fresh observations can form new findings, but pre-reset evidence cannot contribute. Review eviction/gap/missing-transition counters are since the latest review reset; ingestion counters cover the whole injector session. Stale-session and repeated reset requests are inert. Timeout or send failure never clears the view optimistically or retries automatically. Reset does not delete exported files or clear Callmon's separate history.

Data otherwise remains memory-only for the injector session. Clearing Callmon history does not clear the separate bounded intelligence log; detaching ends both. Ordinary launch remains sensor-free; process observation and mixed-output analysis require independent explicit activation. Evidence export includes only the latest reduced acoustic summary and processor accounting when their strict contracts are valid; it does not include PCM, acoustic history, or participant attribution, and acoustic data is not used for automatic actions. No privileged service, cloud telemetry or automatic on-disk identity history is introduced. Community baselines, group-movement rules, calibrated metrics and feedback remain future work. See [the architecture proposal](docs/intellicord-future-architecture.md) for precise implementation status. Rebuild frontend and Rust together. Live compatibility of the new review and acoustic flow remains unverified, and this milestone does not install or activate itself.

### Linux Sensor Prerequisites

The refresh icon in **Safety & Intelligence** requests a read-only Linux prerequisite snapshot. It never starts an eBPF sensor, loads a kernel module, changes permissions or attaches a tracing program. Requests are session-bound, replay-protected and limited to one host check per two seconds. The client times out after five seconds without retrying; late responses after timeout, close or disposal are ignored. Invalid responses clear the previously displayed report rather than presenting stale facts as a successful check.

For testing without Discord or audio capture:

```sh
cargo run --quiet --bin intellicord -- diagnostics
```

The bounded schema-v3 JSON report includes kernel BTF and cgroup-v2 metadata, unprivileged BPF policy, perf-event policy, effective `CAP_BPF`/`CAP_PERFMON`/`CAP_SYS_ADMIN`, the process-exec tracepoint ID's accessibility, kernel lockdown, no-new-privileges and seccomp mode. Missing, unreadable and unknown metadata are not positive readiness verdicts. Process status describes the checking backend's main thread, not every worker or a future separately privileged sensor. BTF presence does not validate its contents, and these facts do not prove program load/attach support. `sensor_running` and `load_test_performed` remain false. The client also accepts schema-v1/v2 reports, marking newer fields unavailable.

No-new-privileges and seccomp are read-only execution-context facts: no-new-privileges prevents gaining privileges across exec, and a seccomp filter may restrict system calls, but its presence alone does not disclose allowed calls. Neither value is a BPF readiness verdict or proof of effective containment. The check installs no policy, changes no credentials and starts no sensor. See [execution context limits](docs/process-observation.md#backend-execution-context).

The standalone preview uses a labeled fixture, not host inspection. Tests cover bounded metadata parsing, malformed values, request/session isolation, rate limits, timeout/cleanup, invalid-report disposal and the executable JSON/argument contract. No privileged operation or live sensor compatibility test is part of this milestone. The optional source-level prototype below advances Aya and the bounded ring handoff; live validation, least-privilege loading, supervised IPC and verified clock correlation remain future work. No custom `.ko` is needed for this prerequisite check.

When investigating test failures, use `node --max-old-space-size=256 --test --test-concurrency=2 tests/*.test.js` to bound individual Node heaps and limit workers. Keep runner flags before filenames: options appended by `npm test -- ...` come after the script's file arguments and may not configure the runner. Assert scalar values or boolean DOM identity checks instead of comparing entire LinkeDOM objects: formatting a failing DOM assertion has previously exhausted system memory.

### Optional Process Sensor Prototype

An optional Aya process-exec sensor now has a shared 24-byte event contract, a separate eBPF source crate, a feature-gated reader and a generated replay command:

```sh
cargo run --quiet --features observe --bin intellicord-observe -- replay
```

The client prerequisite check displays the same **Process-event decoder replay** with explicitly synthetic counters. It does not start tracing or claim kernel compatibility. The optional reader supports deliberately acknowledged, bounded-duration observation of one numeric PID with a trusted, separately built object. Its supplied program filters before writing to a 64 KiB ring and accounts for failed reservations. Normal builds/startup remain sensor-free; no privileges or kernel settings are changed automatically.

An explicitly acknowledged Linux/observe injector mode can connect that bounded
collector to sampled client diagnostics using `--observe-object PATH`,
`--observe-pid PID`, `--observe-seconds 1..60` and
`--acknowledge-injected-observation` together. It requires a compatible
`intellicord-observe` beside the injector. Ordinary `inject` and desktop `launch`
never enable it. Tracking shutdown awaits collector and private-endpoint cleanup;
the final report is printed on detach. No elevation or automatic restart occurs,
and recent counters never establish sensor liveness. Valid-object integration is
unverified: tests use fake DevTools and reject an invalid object before BPF loading.
Read [explicit injected observation](docs/process-observation.md#explicit-injected-observation)
before deliberate use. Do not elevate the authenticated injector to work around
missing collector permissions.

`intellicord-observe inspect --object PATH` checks a trusted object's ELF architecture, program declaration and exact map layout without BPF syscalls. Capture applies the same check before loading. An `observe`-enabled backend can optionally use `INTELLICORD_OBSERVE_OBJECT` for the client's explicit **Process sensor object** check; renderer requests cannot choose paths. Default builds report the optional inspector as unavailable. A layout match is not a verifier, behavior or permission verdict. Generated ELF tests exercise this path without requiring a BPF toolchain; see the guide for commands and limits.

`cargo run --quiet --features observe --bin intellicord-observe -- probe-target` tests pidfd access on the command's own process only, without selecting Discord or loading BPF. The client's explicit check shows the same **Process target safety** result, or reports that the feature is not built. Capture now requires a live pidfd before loading/attachment and stops on visible target exit. This narrows the numeric-PID lifetime gap, but does not bind the BPF filter to a process generation or executable; selection/polling races and namespace assumptions remain. Disposable child-process tests cover exit/reaping without tracing.

The reader and real `bpfel-unknown-none` kernel artifact compile locally, and generated contract/CLI/client tests plus an explicit real-artifact instruction test pass. The explicit live-sensor installer packages the compatible host reader and inspected object together; the ordinary installer still omits them. The operator reported successful load-only, disabled-target attach/detach and controlled-child delivery probes on Linux 6.18.58-1-lts. Sustained supervised collection, overload behavior and crash cleanup remain unverified. PID reuse outside the controlled probe, privilege separation, IPC/clock normalization and authenticated client live status remain unfinished. See [the process observation guide](docs/process-observation.md) before any deliberate live invocation. No Discord process was observed or modified for this prototype.

The Linux reader offers `verify-load --object PATH --acknowledge-bpf-load` for separately authorized kernel verification without attachment. Unlike `inspect`, it can create temporary maps and load the reviewed program; it never selects a target or starts tracing. The operator reported success on Linux 6.18.58-1-lts, establishing load-only acceptance on that host, not general compatibility. Client diagnostics still show only build availability and CLI-only activation, never a successful load claim. ### Offline Acoustic Foundation

[src/acoustic.rs](src/acoustic.rs) provides bounded 20 ms supplied-PCM analysis for RMS, per-channel/max-channel energy, peak, near-full-scale sample ratio, and continuity-aware level differences. The direct analyzer retains no PCM. The separate [frame assembler](src/acoustic/framing.rs) accepts bounded channel-aligned chunks, maps absolute sample positions to timestamps without cumulative rounding drift, retains less than one frame of PCM between calls, and explicitly reports gaps/discarded partial samples. Neither component opens audio devices. Run `cargo run --quiet --example analyze_synthetic_audio` for generated-frame summaries or `cargo run --quiet --example assemble_synthetic_audio` for chunked-input and gap recovery. These are linear level features, not micspam detection, perceived loudness, or speaker attribution. PipeWire capture/consent controls, OS-clock synchronization, robust content fingerprints, scoring, and attenuation remain unimplemented; nothing is connected to the runtime sensor bus or UI. See [the acoustic foundation contract](docs/acoustic-foundation.md) for limits and privacy boundaries.

The optional [spectral analyzer](src/acoustic/spectral.rs) adds power-weighted spectral centroid, a documented 4 kHz high-band ratio, and continuity-aware normalized positive power flux using RustFFT. Run `cargo run --quiet --example analyze_synthetic_spectrum` for generated-only complete-frame summaries. `SpectralFrameAssembler` combines the same chunk/gap handling with spectral analysis; try `cargo run --quiet --example assemble_synthetic_spectrum`. The combined path retains a bounded previous spectrum and less than one frame of partial PCM, and emits no PCM. These features are not repetition matching or micspam scoring. Capture, runtime routing, calibration, and playback protection remain unimplemented.

The [repetition feature helper](docs/acoustic-repetition.md) compares short sequences of coarse spectral descriptors over a bounded 1.1-second history. Run `cargo run --quiet --example analyze_synthetic_repetition` for generated repeated/disjoint sequences, or `cargo run --quiet --example assemble_synthetic_repetition` for chunked input through `RepetitionFrameAssembler`. The combined path computes levels/FFT once per frame and clears repetition history on gaps/reset without emitting PCM. Its best-lag similarity is not content identification, a calibrated abuse score, or proof of repetition. No capture or runtime integration is enabled.

For generated-only processing measurements, run `cargo run --release --quiet --example benchmark_acoustic`. Its JSON separates fresh-assembler startup, warmed all-push latency, and frame-producing push latency across twelve bounded workloads. See [the benchmark method](docs/acoustic-performance.md) for interpretation and limitations; this is not capture validation or a real-time guarantee.

For explicitly supplied recordings, run `cargo run --release --quiet --example evaluate_acoustic -- /path/to/recording.wav`. The [offline WAV evaluator](docs/acoustic-evaluation.md) streams a bounded local file into aggregate features and one final summary, with no capture devices or runtime integration. Strict format/duration limits and known WAV-layout limitations apply; no representative accuracy or detection result is implied.

The [offline acoustic lifecycle](docs/acoustic-session.md) adds explicit activation, per-activation producer permits, and stopped/active/faulted processing state. Stop and invalid active input discard the wrapper's processing history. Permit-checked producer reports can also fault processing for source loss, format changes or input overflow without allowing a stale callback to stop a newer activation. Optional tagged outputs reject delayed results from stopped, faulted or replaced activations at acceptance; final delivery still requires controller synchronization. Restart remains explicit. This is a library boundary for future consent/worker integration, not capture or a user-facing permission control; no device stream or runtime feature is enabled.

`BufferedAcousticSession` adds an optional owning eight-batch FIFO to that offline lifecycle. It preserves gap/partial metadata, clears pending outputs on stop/fault, and faults explicitly on output overflow instead of silently losing summaries. Popped batches remain caller-owned; final delivery still requires synchronization with revocation. No capture, worker or runtime routing is enabled.

The controller's `health()` snapshot reports pending, processed, delivered and discarded batch/frame counts, output overflow events and queue high-water depth. Counters are bounded, memory-only lifetime totals across restart; they measure output disposition, not device liveness or downstream receipt. No features or identifiers appear in the snapshot.

The [offline acoustic helpers](docs/acoustic-foundation.md) also accept bounded raw PCM byte conversion through `decode_pcm_chunk`: explicit little-endian signed 16/packed 24/32-bit or float32, interleaved complete channel groups, at most four frames per call. Conversion returns caller-owned normalized PCM, not features; it does not open files/devices, resample, negotiate PipeWire formats or enable capture.

Use `BufferedAcousticSession::push_bytes` for the lifecycle-managed byte path: it validates the activation permit before conversion, uses the activation's rate/channel count, and clears processing and backlog on current conversion errors. Valid samples follow the existing gap, timestamp, FIFO and health-accounting rules. Encoding remains caller-declared, not verified source negotiation.

Optional `BufferedAcousticSession::start_encoded` binds the expected byte encoding for one activation. A current mismatched `push_bytes` faults as a producer format change and clears pending output; stale callbacks remain inert. Ordinary `start` retains per-call encoding behavior. This checks declared metadata only, not actual source negotiation or consent.

Run `cargo run --quiet --example replay_acoustic_lifecycle` for a generated-only replay of activation, partial/gap processing, queue overflow, source loss, encoding changes and explicit restart. Its JSON reports 26 checked health checkpoints, not PCM or feature traces. See the [lifecycle guide](docs/acoustic-session.md) for expected accounting and limits; this is not capture or a concurrency/performance test.

The [PCM conversion helpers](docs/acoustic-foundation.md) support explicit planar and strided channel views through `decode_pcm_planes`. Checked offsets/ranges and the four-frame output limit apply; padding is ignored and output is normalized interleaved PCM. The [owning acoustic lifecycle](docs/acoustic-session.md) also accepts `push_planes`, applying permit/encoding checks, conversion-fault teardown and shared output accounting. Neither path maps PipeWire buffers, verifies a capture source or opens devices.

The [source-clock helpers](docs/acoustic-foundation.md) map explicitly supplied clock readings into backend monotonic intervals using a bracketed anchor, caller-supplied rate-error bound and source-time horizon. `SampleClockMapping` also maps absolute per-channel sample positions with outward rounding, assuming ideal sample cadence in source-clock time. Optional `TimedRepetitionFrameAssembler` attaches start/end intervals alongside explicitly nominal features, rejecting timing failures before processing. These helpers do not read or calibrate clocks. Capture, lifecycle and fusion integration remain unfinished.

The timed assembler also accepts `push_bytes` and `push_planes`, reusing the bounded PCM converters and preserving interval-bearing output. Conversion and timing errors reject input without consuming buffered samples; encoding is caller-declared per call. The separate [TimedAcousticSession lifecycle](docs/acoustic-session.md) binds one clock mapping to a fresh activation permit, optionally binds encoding, faults on current input errors and requires consuming tagged-output acceptance. Its owning `BufferedTimedAcousticSession` variant adds an eight-batch FIFO, explicit overflow teardown and lifetime output-health accounting. Neither provides runtime capture integration or synchronized final delivery.

Run `cargo run --quiet --example replay_timed_acoustic_lifecycle` for a generated-only replay of interval delivery, clock expiry, overflow, producer/encoding faults and fresh activation. It validates conservation at 31 fixed checkpoints and emits health-only JSON after successful checks. It accepts no arguments, reads no input files or devices, and does not establish capture compatibility or calibrated synchronization. See the [timed replay contract](docs/acoustic-session.md).
